# 流式翻译基线与优化对比

## 测量边界

这是一组可重复的虚拟时钟调度基准，不是商业 API 延迟、Chrome 绘制速度或真实网站的性能承诺。
测试使用真实的 DOM 扫描器、服务入口、批处理队列、请求池、OpenAI 请求构建、行协议流式解析和业务回调；替换的是网络传输、缓存及浏览器可见性通知。
首词指业务 `onStreamChunk` 首次返回译文字符，不包含浏览器绘制和扩展 Port 的传输耗时。JSON 增量解析依赖由空实现替换，基准使用真实的 `ID | Text` 行协议解析，不测试 JSON 协议的性能。

`before.json` 是修改性能代码前实际运行保存的结果；`after.json` 是优化后相同固定条件的结果。当前代码的 `pnpm bench:stream` 只更新 after 结果；不要把当前代码运行结果标记成 before。

## 固定条件

- 12 个英文段落，全部冷缓存；前 5 段定义为首屏完成统计对象。
- 同一页面内容、模型参数、批量大小 20、字符上限 10000、批次等待 150ms、扫描间隔 100ms。
- 可见性通知故意以非阅读顺序，每 10ms 到达一个，用于检验连续通知下的等待和排序。
- 模拟服务响应等待 180ms，每 20ms 输出一个协议片段，每段输出三个片段。
- 分别使用 1、2、4 的请求及批处理并发上限。正常场景没有注入服务错误。
- 时钟步进为 5ms；这些数值是该模型下的调度结果，不是多次真实网络采样的均值或置信区间。

## 并发 2 的主对比

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 任意段落首词回调 | 585ms | 345ms | 减少 240ms，41.0% |
| 顶部第一段首词 | 1005ms | 345ms | 减少 660ms，65.7% |
| 首屏前 5 段完成 | 1025ms | 545ms | 减少 480ms，46.8% |
| 全部段落完成 | 1265ms | 935ms | 减少 330ms，26.1% |
| 请求数 | 1 | 2 | 小首批带来一次额外请求 |
| 实际峰值并行请求 | 1 | 2 | 使用了配置已有的第二个槽位 |

优化前译文出现顺序：`7, 6, 5, 4, 3, 2, 1, 0, 11, 10, 9, 8`。
优化后：`0, 1, 2, 4, 3, 5, 6, 7, 8, 9, 10, 11`。

当前策略优先从上到下提交，不为了绝对输出顺序缓存已经完成的译文。并行批次仍可能小幅交错，例如本例第 4 段先于第 3 段；严格串行显示会人为增加首词等待。

## 并发选择与代价

| 并发上限 | 优化后首词 | 顶部首词 | 首屏完成 | 全部完成 | 请求数 / 实际峰值 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1 | 475ms | 475ms | 735ms | 1155ms | 1 / 1 |
| 2 | 345ms | 345ms | 545ms | 935ms | 2 / 2 |
| 4 | 345ms | 345ms | 545ms | 935ms | 2 / 2 |

本例并发 4 没有额外收益，因为优化后只有两个批次。这不足以推断长网页的最佳并发数，因此保留批处理默认并发 2，不提高用户配置的并发上限。
小首批仅用于实时流式、无历史上下文依赖且批处理并发大于 1 的请求。首批最多 4 段，最多等待 16ms；后续继续使用已有批量设置。串行模式不拆小首批，避免额外请求拉长整页完成时间。
额外请求可能重复系统提示词并增加计费开销，不能将减少等待时间等同于成本降低。

## 实现与稳定性

- 可见性调度改为固定收集窗口，连续通知不再不断延后启动；先处理实际视口内节点，再按文档顺序处理。
- 待发送批次按段落阅读位置重新排序，修正跨收集窗口晚到节点的次序。
- 后续批次可以在首批流式响应期间启动，始终受批处理上限、接口请求池和全局闸门约束。
- 同一接口出现可重试 429 后，整个请求池进入冷却，新任务也等待。已在途请求不强行中止。
- 保留取消不重试、部分流式输出后不自动重放、配置/上下文/会话隔离等规则。

专项回归覆盖取消、限流冷却和并发边界；当前基准不包含真实负载样本，不能据此声称真实限流率、失败率或稳定性提升了某个百分比。

## 复测

```bash
pnpm bench:stream
```

真实服务测量需要有效的 LingoFlow 接口配置，并使用同组短文本和相同模型采样，记录端到端首词、完成时间、HTTP 状态与实际请求数。这里的结果不包含真实服务和浏览器绘制数据。
